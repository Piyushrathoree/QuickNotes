# QuickNotes Android implementation plan

Implementation handoff for **GPT-6 Luna, xhigh reasoning, Fast**. Build an Android-only React Native app with Expo and distribute a standalone signed APK from the official QuickNotes site. Keep the Next.js app at the repository root and put the Expo app in `apps/mobile/`. Both clients use the existing QuickNotes accounts and Neon database. Use the existing pnpm workspace and build the web app and APK independently.

## Scope and release sequence

1. Prove signed APK installation and existing-account authentication on a real Android device against staging.
2. Build guest notes, native Markdown editing and preview, local drafts, and file export.
3. Introduce conflict-safe cloud writes across web, Android, and MCP. Add mobile account notes and guest import.
4. Run a private APK beta. Fix data integrity, update, and device issues before opening the download.
5. Publish the Android APK and official install instructions when the release checks pass.

The beta includes guest use, notes list, editor and preview, local persistence, Markdown and text export, email/password sign-in and signup, browser-based password reset, explicit cloud save, online cloud delete, and guest import. Include light/dark/system appearance and an account/settings screen. Keep the writing experience focused on immediate entry into a note. Schedule public link management, custom writing fonts, and in-app update notices after the core beta. Existing public links continue to open on the web. Future work includes iOS, live inline Markdown styling, automatic background cloud sync, notifications, widgets, and native Connect AI management.

## 2. First integration milestone

Use an HTTPS staging origin with an isolated Neon database and test accounts. Reserve `https://www.quicknotes.site` for production builds. Start with a staging package ID distinct from the production ID so both APKs can coexist. Propose `site.quicknotes.app` for the production application ID, verify it before use, and record it before the first distributed production APK. Use a separate staging signing key.

1. Build a standalone release-mode staging APK locally. Serve it by HTTPS and use a real device to download, install, and launch it with developer options off. Confirm no Metro, Expo Go, or development server is needed. Install a second build with the same package ID and signing key and a higher `versionCode`.
2. Test Better Auth's matching Expo server and client integration with the version in the lockfile. Add the Expo server plugin while keeping `nextCookies()` last, lazy initialization intact, and existing exact web origins accepted. Use the documented mobile scheme and the minimal origin changes needed by that version. Keep the existing auth endpoint and account database. Verify web signup, login, logout, and password reset in staging. [Better Auth Expo integration](https://better-auth.com/docs/integrations/expo)
3. Sign in from the APK with an account created on the web, restart the app, load an existing note through the authenticated API, and prove a test note can round-trip between web and phone. At this milestone a staging-only integration test can use the present write contract. Public builds must use the revised contract below.
4. Centralize authenticated mobile fetches. Use Better Auth's Expo credential handling with SecureStore and the documented cookie forwarding for notes requests. Attach credentials solely to the configured API origin, use canonical HTTPS URLs directly, and reject redirects for authenticated API calls. Use the browser for account recovery with the existing `/forgot-password` flow. After recovery, the user signs into the Android app again.
5. Verify an expired or revoked session returns the app to sign-in on the next verified response. Treat a timeout or offline startup as a connection state. Keep cached account access tied to the last locally verified account with no sign-out, and verify the session when the network returns. A confirmed 401 locks account content immediately and retains account-scoped drafts for that user's return. Log status and request identifiers where helpful. Avoid collecting cookies, passwords, note text, and sensitive URLs.

Record device model, Android version, build version, origin, install source, and results. If hardware is unavailable, use an emulator to continue development and keep real-device evidence pending. Troubleshoot dependency compatibility or credentials in staging without broadening auth rules.

## 3. Screens and device persistence

| Screen | Required behavior |
|---|---|
| Editor | Open the previous active note or a blank editor. Create durable storage when the user types meaningful content. Derive the title from the first line. Provide Edit and Preview, keyboard-compatible controls, formatting for headings, emphasis, lists, checkboxes, links, and code, and file export. |
| Notes list | Show guest or account notes by recent activity with a stable tie-breaker. Indicate unsent drafts and cached versus unavailable bodies. Provide new note, open, refresh for account mode, and confirmed delete. |
| Account | Offer sign-in and signup with the current server's validation and neutral auth errors. Link to the website for password reset and account management. Present the import decision when guest notes exist. |
| Settings | Provide appearance, account controls, version, and official Android release page. Include wording that guest notes and unsent drafts can be lost when the app is uninstalled or its data cleared. |

- Preserve selection, scroll position, and the exact Markdown text across preview toggles. Apply formatting to the selected range and handle Android keyboard resize, IME composition, TalkBack, large system fonts, Android Back, and small screens. Format actions need accessible labels. Editor interactions must remain responsive for large notes. Preview rendering should not run on every keystroke while the editor is visible.
- Persist authoritative local drafts in SQLite. Use app-private storage and parameterized queries, numbered migrations, and transactions for updates involving multiple records. Keep per-scope active note and storage keys, with one guest scope and separate scopes for each authenticated user. Track stable UUID, content, local edit sequence and time, server base revision, and server snapshot or cache state as applicable. Store note summaries independently of downloaded bodies or model that distinction explicitly in one table. Store only session material in SecureStore.
- Save text asynchronously as it changes. Serialize writes for each note, and ensure a delayed earlier write cannot overwrite a later edit. Flush pending writes before navigation and on background where possible. Test immediate force-stop after the device-saved indicator. Display that indicator only after persistence succeeds. Retain text in memory and surface a clear save error if storage fails, with export available as a recovery path.
- Refresh account summaries on launch, foreground when appropriate, and pull-to-refresh. Load uncached bodies on demand. Use cached bodies offline. Treat summary absence as deletion evidence only for a completed authoritative list response. Never remove a dirty draft during refresh. A failed fetch must preserve the previous cache. Use a session generation or equivalent guard so a slow response from user A cannot update user B's active state or storage.
- On deliberate sign-out, offer export of unsent work and a clear choice about discarding it. Lock retained data to the same account and clear local session credentials even if the server sign-out request fails. When online, revoke the current server session through Better Auth. Keep an earlier account's titles, content, and pending operations out of guest views and other accounts. Handle Android backup explicitly so restored local data or unusable SecureStore credentials cannot expose prior accounts. Decide and document whether device notes are excluded from Android backup.
- Export the current draft, including unsaved edits, as UTF-8 Markdown or plain text. Sanitize the file name, use the matching MIME type, let Android's share sheet grant file access, and clean up temporary files after recipients have had a chance to read them. Test guest export offline. Keep the original note bytes in storage, including Unicode, multiline text, and pasted Markdown.

## 4. Cloud contract and rollout

Read the existing implementations before editing. The relevant paths are `src/app/api/notes/route.ts`, `src/app/api/notes/[id]/route.ts`, `src/app/api/notes/_shared.ts`, `src/lib/sync/client.ts`, `src/lib/sync/migrateGuest.ts`, `src/lib/store/cloudSession.ts`, `src/lib/store/cloudState.ts`, `src/lib/mcp/notesRepo.ts`, `src/lib/shares/index.ts`, and `src/db/schema.ts`.

The current API orders writes by a client timestamp, may return HTTP 200 with a different server snapshot when it declines a write, and can implicitly restore deleted notes. Web Undo relies on that restore path. MCP update and append read then write note content and can race with other writers. Resolve those paths together before public Android writes.

### Data and atomicity

- Add a positive, server-issued integer `revision` to notes via an additive Drizzle migration. Backfill existing live and deleted rows to revision 1. Return revisions on summaries and bodies. Increment revision inside the same database write as content, delete, or restore. Use server write time for new `updatedAt` values. Treat timestamps as display and sorting metadata. Verify schema and migrations locally against existing data before staging.
- Match note ID, authenticated owner, expected revision, and live/deleted state in the mutation predicate. Use the database's conditional mutation result as the authority. Avoid a preflight read followed by an unconditional write. Fetch an owner-scoped snapshot after a failed predicate to shape the error. Keep other owners' rows indistinguishable from absent rows. Preserve session authorization, UUID validation, no-store responses, and the existing **1 MiB UTF-8** maximum. Use a stable machine-readable error code in addition to display text.
- Bring MCP write paths through the same invariants. MCP creates start at revision 1. Update/append must use compare-and-set with a bounded re-read and recomputation for operations defined against the current row, or an atomic SQL mutation. Preserve MCP schemas and response behavior where viable. Verify deletion and restoration advance revisions on real state changes, including changes initiated through MCP.

### Proposed route behavior

Use the existing URLs for list, detail, and writes and add a dedicated restore action. Names can follow the installed Next.js route conventions while preserving these semantics.

| Request | Contract |
|---|---|
| `GET /api/notes` and `GET /api/notes/:id` | Return owner-scoped live notes with `revision`. Keep list results as summaries. Detail returns the full body. |
| `PUT /api/notes/:id` with `baseRevision: null` | Create at the client-generated UUID. Repeating the same create against an existing live note with identical content may acknowledge it without changing it. An owned UUID with different content or a tombstone produces a conflict. A UUID owned by another account returns a generic 404. |
| `PUT /api/notes/:id` with `baseRevision: number` | Update a live note at that revision. Return the accepted snapshot and its new revision. Report an owned live mismatch or owned tombstone as 409 with enough owner-scoped state to recover. Return 404 for missing or other-owner IDs. |
| `DELETE /api/notes/:id` with an expected revision | Soft-delete a matching live note and return the committed deletion revision needed for Undo. Return a conflict for an owned tombstone or a stale revision. If a delete response is lost and refresh finds a tombstone, the UI can show the note as deleted. Offer Undo only when the client received the committed deletion revision from its own successful delete. Choose a single documented way to carry the expected revision, such as a validated query parameter. |
| `POST /api/notes/:id/restore` | Restore an owned tombstone only at the submitted deletion revision. Return the new live note. Web Undo may explicitly submit its preserved draft with the restore action to retain today's behavior. A stale restore must conflict without replacing newer content. |

Malformed input receives 400, missing authentication receives 401, oversized input receives 413, unsupported content type receives 415 where relevant, and a transient backend failure receives a retryable service error. Document exact request and response schemas in implementation and keep app and server validation aligned.

### Web compatibility and cutover

- Stage the additive migration first. Update the web client, cache logic, session layer, guest migration, and Undo together with the backend contract. For cached entries from before the migration, preserve dirty text, fetch the current server baseline before writes, and bind an old draft to a new revision only when its saved base can be verified. Otherwise present the remote and draft as a conflict. A dirty legacy draft with unknown origin is never a license to overwrite current server text.
- If deployment requires a short period accepting the timestamp contract, keep it confined to the transition. Once revision enforcement is active, return a recognizable refresh-required error for stale web clients that still submit legacy writes. Keep their locally persisted drafts recoverable on reload. Confirm fresh web clients use revisions and verify the stale-tab experience before releasing mobile cloud writes.
- Test migrations on existing notes, shares, and tombstones. Confirm public share links for live notes, current delete/restore visibility, web saved-state indicators, and web Undo still work. Enforce the revised contract on all supported interactive mutation paths before the public APK. Any rollback must account for already-installed clients and preserve the additive revision column and compatible routes.

## 5. Mobile save, delete, and import

- **Explicit Save.** Typing changes only the local draft. Save requires a verified account and submits the captured content and base revision. Disable duplicate in-flight saves for the same note. Keep draft state durable across timeouts, transport errors, and app death. If the user types during a successful save, advance the baseline to the acknowledged snapshot and retain the newer local draft as unsent. Guard response application against account switches and stale refresh responses.
- **Conflicts and uncertain outcomes.** Keep the remote and draft distinguishable. Offer **Keep draft as a copy** with a fresh UUID and **Use cloud version** with explicit confirmation before discarding local text. If a request may have committed despite a missing response, fetch current state first. If the current live content matches exactly what was submitted, the submitted text is present and the client can adopt that snapshot while preserving later local edits. If it differs or the note is deleted, follow the conflict flow. Never retry an edit by silently replacing its expected revision with the current revision.
- **Delete.** Local guest or never-uploaded drafts can be removed on the device after confirmation. Cloud delete requires connectivity and a known revision, and updates the list only after success or confirmed already-deleted state. Serialize cloud delete with same-note saves. Ask explicitly before discarding unsent text or preserve it as a separate local draft. An external delete must never be undone by mobile refresh or save.
- **Guest import.** Offer import or keep on this device when a user signs in. Keep declined and unsuccessful drafts accessible in the guest workspace and give the user a later entry point to import. Pin an import attempt to its destination account and a stable UUID per source note. Clear the source only after confirming equivalent live cloud content and checking the local edit sequence still matches what was sent. Keep the guest copy when the source changed during import, the server returns different content, or the result remains uncertain. Resume a partial import without duplication after app restart or manual retry, and avoid sending remaining items after an account switch. If a pinned attempt belongs to another account, require a new explicit import decision before assigning new destination IDs.
- **Feedback.** Distinguish **Saved on device**, **Saving to account**, **Saved to account**, **Offline**, **Sign in to save**, and **Conflict**. The cloud indicator reflects the visible draft's actual state. Failed saves must leave an actionable error and an available draft.

## 6. APK signing and distribution

- Generate a release key controlled by the project owner and keep an encrypted backup. Use separate staging signing. Keep signing files and passwords out of Git, logs, and artifacts. Use the same production ID and certificate for each release and allocate strictly increasing Android `versionCode` values. Build a release APK with a bundled JavaScript payload using the documented Gradle release task, normally `:app:assembleRelease`. Verify with `apksigner verify --print-certs` and record SHA-256, app ID, SDK requirements, version code/name, build commit, and file size. Inspect the release manifest for debugging, cleartext, and unnecessary permissions. [Expo local release builds](https://docs.expo.dev/guides/local-app-production/) · [Expo APK output](https://docs.expo.dev/build-reference/apk/) · [Android app signing](https://developer.android.com/studio/publish/app-signing)
- Publish an official `/android` page after a signed artifact is ready. Serve the APK over HTTPS at a versioned URL using a release asset host if needed. Show version, supported Android range, release notes, checksum, and actual install steps. Verify the downloaded bytes match the locally signed APK and that Android can install them from the documented path. Use the same page for manual updates and publish hotfixes with a higher `versionCode`.
- Check developer verification in the intended launch markets early and again at release. As of Google's November 19, 2026 announcement, the global rollout begins in January 2027, Android's advanced flow lets users install unregistered apps where applicable, and the free limited account covers up to 50 authorized devices. Google's full off-Play account FAQ lists a US$25 fee. Keep the zero-budget route as a signed direct download, document extra steps where needed, and use the web app as the fallback when a device or user cannot complete installation. Never promise universal one-tap installation. [Google's rollout announcement](https://developer.android.com/blog/posts/android-developer-verification-2027) · [Google's verification FAQ](https://developer.android.com/developer-verification/guides/faq?hl=en)

Add targeted automated regressions for database revision races, stale delete/restore and account ownership, web cache migration, and mobile save/import reconciliation. Use integration tests against an isolated database for guarantees that depend on SQL atomicity. Keep a manual device checklist for UI and install behavior. Record any unrun check as pending.

The implementing agent's handoff should identify app and backend changes, any migration and deployment ordering, the exact build and verification commands, APK location and identity, device test evidence, and open release gates.
